# Як долучитися

## Модель гілок

```
main  ────●──────●────────●──────   актуальний стан; релізи — теги 5.0.2-1, 5.0.2-2, …
           \    /          /
translate/ui ●──●          /       гілка під задачу → PR у main → гілка видаляється
fix/typos        ●───●───●
```

- **`main`** — єдина постійна гілка. Прямі коміти заборонені, лише через PR.
- **`translate/<що>`**, **`fix/<що>`** — гілки під конкретну задачу; створюються від `main`, після злиття видаляються.

Реліз: тег `<версія-гри>-<номер>` на `main`, запис у [CHANGELOG.md](CHANGELOG.md), файл у Releases.

## Воркфлоу

1. Перегляньте [translation/GLOSSARY.md](translation/GLOSSARY.md). Терміни з глосарію перекладаються **тільки** так, як там зазначено. Новий термін або зміна — правка `translation/glossary.tsv` + `python tools/glossary.py` (перегенерує MD), окремим PR.
2. Виберіть файл/розділ в issues (або створіть issue, щоб ніхто не робив те саме паралельно).
3. Від `main` створіть гілку `translate/<назва-файлу>` або `fix/<коротко-що>`.
4. Перекладайте у [translation/strings.tsv](translation/strings.tsv): заповнюйте колонку `translation`, колонки `file`, `key`, `original` не чіпайте. Книги та списки імен — у `translation/files/` (звичайні текстові файли). `source/` не редагується.
5. Перевірте в грі: `python tools/build.py --install` (з `--drafts`, щоб побачити й чернетки), у грі Custom Content → Local Mods → uk-UA → Load Mod. Перед PR запустіть `python tools/validate.py` — перевірка плейсхолдерів. `build.py` також перевіряє ліміти гри: JSON читається у буфери фіксованого розміру (`JSON_SIZE_LIMITS` у `tools/barony.py`), запис `en.txt` — до 1024 байт; якщо білд скаржиться на розмір — тексти в тому файлі треба скоротити.
6. Відкрийте PR **у `main`**. В описі вкажіть, що перекладено і чи є спірні місця.

## Правила для PR

- Один PR — одна логічна частина (напр. один файл зі `strings.tsv`: `lang/item_names.json`, або одна книга). Великі PR важко рецензувати.
- Колонка `status`: порожня — переклад готовий; будь-що інше — чернетка, що в мод не потрапляє (`fuzzy` — не вичитано, у Weblate «needs editing»; `unresolved` — у рядку є термін без затвердженого перекладу в глосарії). Приймаючи чернетку, очистіть `status`.
- Глосарій: `id` не змінювати (на нього посилається колонка `entities`); `status` порожній — термін затверджено, `fuzzy` — переклад не вичитано, `new` — перекладу ще нема. Затвердження — очистити `status`.
- Перед перекладом прочитайте [translation/STYLE.md](translation/STYLE.md); контекст рядка — у колонці `context` (у Weblate — коментар під оригіналом). Якщо контексту бракує або він хибний — правте колонку, це теж внесок.
- Не змінюйте ключі, плейсхолдери (`%s`, `%d`, `%+d%%`), `$` (значок клавіші в навчальних табличках), назви дій у дужках на кшталт `[Attack]`, `\n` і службові символи сюжетних текстів (`#` — пауза, `^` — зміна картинки, `*2` — розмір).
- Рядки JSON часто нарізані по одному рядку екрана (`blurb/0`, `blurb/1`, …) — стежте за довжиною, щоб текст не вилазив за рамку.
- Не перекладайте те, чого немає в оригіналі, і не додавайте відсебеньок.
- Спірні варіанти залишайте коментарем у PR, а не в тексті перекладу.

## Автоматичні перевірки

На кожен PR у `main` GitHub Actions запускає `tools/glossary.py --check`, `tools/validate.py`, перевіряє, що `translation/` відповідає `source/` і `glossary.tsv` (тобто після правок запущено `extract.py`/`glossary.py`), і що мод збирається. Червоний PR не зливається.

## Рецензування

Кожен PR перевіряє щонайменше одна інша людина: стиль, орфографія, збереження технічних елементів, узгодженість термінів з уже перекладеним.
